### Merge order
Stacked on #113 (the storage pool), which is stacked on #94 (exact establishment counts). It needs #94's per-node weights: develop's birth-date build is a trapezium over neighbouring nodes, which cannot be reordered. It does work only once #113 is in: on #94 alone no realistic run crosses.

### The problem, in the model's terms
A crown shades only below its top, so the light at height z sums the cohorts taller than z. With heights falling down the node list, that is one running total per build, merged against the ascending knots. When two cohorts born close together swap heights, the build gave up the running total and evaluated every crown at all 65 knots.

### What changes
- `field_splits_nodes`, birth-date branch only. If the height scan reports the list out of order, `order = ascending_by_abscissa()` (tallest first); otherwise `order` is empty, meaning list order, as in `reduce_competition`.
- The running total and the count of nodes reaching each knot index through `order`. Each node's term is unchanged; only the order of summation changes.
- The height coordinate still evaluates every crown when crowns cross, because its trapezium's grid is the node order itself.
